# Task Scope

작업을 사용자가 확인할 수 있는 흐름으로 나누고, 첫 구현을 시작할 조건을 정합니다. 전체 스펙 완성을 기다리지 않습니다.

## 입력과 기록

사용자 요청, 프로젝트 지침, 현재 파일과 변경 사항, 기존 결정, 주어진 시간 제약을 먼저 확인합니다. 코드나 문서에서 찾을 수 있는 답은 직접 확인합니다.

프로젝트에서 지정한 기록 형식과 기존 경로를 우선합니다. 없으면 현재 흐름의 요구와 가정은 `docs/specs/<topic>.md`, 작업 체크리스트는 `docs/plans/<topic>.md`, 실행 결과와 이상 상황은 `docs/reports/<topic>/<work-id>.md`에 둡니다. 같은 정보의 원본은 한 곳에 두고 요구 ID로 연결합니다.

기존 `WORK.md`나 작업 장부의 과거 기록은 유지하며 자동 이관하거나 복제하지 않습니다. 새 플랜은 체크리스트와 원본 링크만 담고, 보고를 누적하지 않습니다. 기존 장부가 있으면 새 보고서에 연결합니다. 한 파일 기록을 요청받았을 때만 [빈 작업 기록](references/work-template.md)을 사용합니다. 문서별 편집 책임은 한 명에게 두고 메인이 최종 통합합니다.

## 질문 선별

| 상황 | 처리 |
| --- | --- |
| 답에 따라 현재 흐름의 성공 조건이나 데이터, 권한, 저장 의미가 변경됨 | 지금 질문, 바뀌는 구현 결정 명시 |
| 되돌리기 쉬운 문구, 배치, 보조 기능 | 가정을 기록하고 진행 |
| 다음 흐름이나 제외 범위에만 해당 | 보류, 다시 확인할 시점 기록 |
| 기존 코드나 제공 자료에 답이 있음 | 확인 후 근거 기록 |

질문은 결정에 필요한 최소 묶음으로 제시합니다. 막연한 예외 목록이나 전체 기능 인터뷰로 넓히지 않습니다. 답이 필요한 작업은 기다리되 독립적인 작업은 계속합니다. 시간 경과를 답변이나 승인으로 해석하지 않습니다.

## 작업 분해와 종료 조건

각 작업은 입력부터 규칙, 저장 또는 결과 표시까지 연결되는 작은 흐름으로 나눕니다. 기술 계층별 작업은 그 흐름 안의 구현 책임으로 배치합니다. 현재 흐름, 다음 흐름, 제외 범위를 구분합니다.

다음 네 항목을 확인할 수 있으면 현재 흐름의 범위 결정을 끝냅니다.

1. 사용자가 수행할 행동
2. 성공했다고 판단할 관측 가능한 결과와 수용 조건 ID
3. 필요한 입력과 상태 변화
4. 실패 시 허용되는 처리

이미 확정된 조건을 다시 인터뷰하거나 별도 설계 승인 절차를 추가하지 않습니다.
구현까지 요청받았다면 수용 조건과 체크리스트를 연결하고 해당 범위의 구현을 이어갑니다. 앱이나 CLI를 새로 구현할 때는 첫 실행 전에 최소 로그 경로와 수집 확인을 첫 작업으로 둡니다.
문서만 다루는 작업에는 로거 설치를 추가하지 않습니다.
이 스킬만 설치되어 있어도 직접 수행할 수 있습니다. 범위 결정만 요청받았다면 다음 작업을 제시하고 마칩니다.

## 반환할 내용

- 첫 흐름과 수용 조건, 관련 근거
- 지금 필요한 질문과 그 답이 바꾸는 결정
- 가정, 보류 항목, 제외 범위
- 다음 작업, 검증 방법, 진행 가능 여부

진행이 막혔다면 빠진 조건과 영향을 받는 작업을 특정합니다. 질문 수나 문서 양을 완료 기준으로 삼지 않습니다.
