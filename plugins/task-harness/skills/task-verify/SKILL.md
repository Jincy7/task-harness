# Task Verify

수용 조건마다 구현 위치와 현재 상태의 실행 근거를 대조합니다. 완료 주장의 범위는 실제 확인한 범위로 제한합니다.

## 확인 절차

1. 요청, 프로젝트 지침, 기존 작업 기록에서 수용 조건과 제외 범위를 확인합니다. 조건이 없으면 제공된 요구에서 관측 가능한 조건을 정리하되, 중요한 업무 의미를 임의로 확정하지 않습니다.
2. 각 조건의 구현 위치와 검증 방법을 연결합니다. 현재 코드에서 실행한 명령, 작업 위치, 종료 결과, 기대와 실제 관측을 기록합니다. 이전 보고는 당시 근거로 구분하고 현재 통과로 재사용하지 않습니다.
3. 정상 흐름과 주요 실패 경계를 검사합니다. 단위 테스트, HTTP/API 통합 테스트, 빌드 등 현재 환경에서 가능한 검사를 먼저 수행합니다. 스크린샷만으로 저장이나 업무 규칙의 성공을 추론하지 않습니다.
4. 실패는 입력, 재현 명령, 기대 결과, 실제 결과를 남깁니다. 수정까지 요청받았다면 원인을 좁혀 수정하고 영향받는 검사를 다시 실행합니다. 검토만 요청받았다면 구현을 바꾸지 않습니다.
5. [검증 기록](references/verification-template.md)의 필요한 부분으로 별도 작업 보고를 작성합니다.
   지정 형식이 없으면 `docs/reports/<topic>/<work-id>.md`에 기록하고 스펙의 요구 ID와 연결합니다.
   플랜에는 체크 상태와 보고서 링크만 갱신하며 결과 표나 실행 이력을 쓰지 않습니다.
   검증 실행기를 수정하는 작업에서는 실행별 로컬 결과 파일을 만들고 플랜 본문을 수정하지 않게 합니다. 검토만 요청받았다면 기존 실행기의 문서 변경 부작용을 확인하고, 기록을 바꾸지 않는 실행 옵션이나 복사본을 사용합니다.

기존 근거와 결정을 보존합니다. 결과의 원본은 작업별 보고 한 곳에 두고 기존 장부와 원본 로그는 링크합니다. 같은 작업의 재시도는 실행 ID로 구분하고 다른 작업 결과를 한 보고서에 계속 덧붙이지 않습니다.

로그가 있으면 대상 코드와 실행 ID, 수집 상태를 먼저 확인합니다.
ERROR, 예상 밖 종료 코드, timeout, assertion 실패와 로그 누락을 이상 후보로 봅니다. 테스트에서 사전에 의도한 오류와 실제 실패는 해당 case의 기대 결과와 assertion으로 구분합니다.
테스트 origin만으로 오류를 무시하거나 정상 로그만으로 통과를 선언하지 않습니다.
같은 증상은 묶고 대표 근거를 연결합니다.
로그가 없다면 가능한 명령 검증을 수행하고 관측 공백을 명시합니다.
검토만 요청받았을 때 새 로거를 설치하지 않습니다.

원인 가설과 확인된 원인을 구분합니다. 제안한 해결책과 실제 적용한 조치를 나누고, 동일 조건의 재현 및 영향받는 회귀 검증이 확인되어야 해결로 표시합니다. stderr에서 error라는 단어가 보인 것만으로 제품 실패를 판정하지 않습니다.

파일 변경이 금지된 읽기 전용 요청에서는 기록 파일도 수정하지 않고 같은 내용을 응답으로 반환합니다.

## 판정

| 상태 | 기준 |
| --- | --- |
| 통과 | 현재 대상의 관측이 수용 조건 충족을 뒷받침함 |
| 실패 | 실행 결과가 수용 조건과 다름 |
| 미확인 | 미실행, 의존성이나 도구 오류, 환경 제한, 필요한 근거 부족 |

명령을 실행했다는 사실과 제품 검증 성공을 구분합니다. 테스트 러너가 시작되지 않았다면 검사 실행 실패와 원인을 기록하고 제품 조건은 미확인으로 둡니다. 일부 조건만 확인한 테스트는 그 범위만 통과입니다. 필수 조건에 실패나 미확인이 있으면 전체 완료를 주장하지 않습니다.

## 사람 확인과 종료

사람 확인은 업무 의미 판단, 직접 사용해야 드러나는 UI 문제, 환경 제약으로 자동 실행할 수 없는 경우에 남깁니다. 각 항목을 `조작 → 기대 결과 → 사람이 확인해야 하는 이유`로 작성합니다. 사람이 확인했다는 답을 받기 전에는 미확인입니다. 브라우저 자동 조작을 기본 단계로 추가하지 않습니다.

수용 조건별 통과, 실패, 미확인을 모두 연결한 뒤 결과와 다음 행동을 반환합니다. 검증 작업을 마친 것과 제품이 완료된 것을 구분합니다. 필수 흐름의 실행 방법, 주요 결정과 코드 위치, 확인한 실패 사례, 남은 한계를 짧게 설명합니다.

별도 모델이나 외부 서비스 연결, 로그 업로드, 자동 Push와 PR을 검증 단계에 추가하지 않습니다. 설치 환경의 권한과 사용자의 요청 범위 안에서 진행합니다.
