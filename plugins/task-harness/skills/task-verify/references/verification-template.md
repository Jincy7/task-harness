# 검증 기록

`docs/reports/<topic>/<work-id>.md` 또는 기존 작업 보고 경로에 필요한 부분만 사용합니다. 플랜에 이 표를 넣지 않습니다. 빈 결과를 통과로 해석하지 않습니다.

- 검증 대상과 변경 상태:
- 관련 스펙과 플랜:
- 실행 ID, 원본 출력과 로그 위치, 수집 상태:
- 검증 시점:
- 작업 위치와 실행 환경:

| 수용 조건 ID | 구현 위치 | 명령 또는 조작 | 기대 결과 | 실제 관측과 종료 결과 | 통과 / 실패 / 미확인 | 한계 또는 다음 행동 |
| --- | --- | --- | --- | --- | --- | --- |

## 행동 시나리오의 근거

현재 수용 조건에 필요한 시나리오만 기록합니다. 같은 조건의 정상 흐름과 실패 후 재시도 등은 사례 ID로 구분합니다.

| 사례 ID / 수용 조건 | 사전 상태와 입력 | 행동 순서 | 기대 상태 전이와 최종 결과 | 실제 응답, 화면 또는 저장 상태 | 실행 및 작업 ID와 원본 근거 | 검증 수준 / 판정 |
| --- | --- | --- | --- | --- | --- | --- |
| | | | | | | |

검증 수준은 UI 직접 조작, API 통합, 단위 또는 합성 계측 확인으로 표시합니다. 위 표로 기존 수용 조건 표를 충분히 설명하면 표를 중복 작성하지 않습니다. 성공 로그와 독립적인 결과 관측을 구분하고 수집 누락이 판정에 미친 영향을 명시합니다.

규칙이 혼동되는 사례는 바꾸는 입력과 고정하는 조건, 달라질 결과와 유지할 결과를 같은 표에 적습니다. 실패 출력에는 기대 및 실제의 원문 위치와 비교 규칙, 확인 가능한 첫 불일치 경로를 연결합니다. 외부 검사가 이를 제공하지 않으면 원인 미확정으로 남깁니다.

## 이상 상황과 해결

필요한 사건만 기록합니다. 같은 증상을 매번 새 사건으로 만들지 않고 횟수와 대표 근거를 연결합니다.

- 사건 ID, 관련 조건과 상태: 조사 중 / 원인 확인 / 조치 후 미검증 / 해결 / 미해결
- 현상, 기대 결과와 실제 결과:
- 입력과 사전 상태, 재현 명령, 실행 ID와 증거 위치:
- 예상한 실패인지와 그 판단 근거:
- 원인 가설 / 확인된 원인과 근거:
- 제안한 해결 방안 / 실제 적용한 조치:
- 수정 후 재검증 실행 ID, 결과와 영향받는 회귀 확인:
- 남은 한계와 다음 확인:

원본 로그 전체와 대화 이력을 본문에 복사하지 않습니다. 수정 전후 근거를 연결하고 로그 누락, 도구 실패와 제품 실패를 구분합니다.

## 사람 확인

확인 대상의 버전과 주소, 입력 및 초기화 방법을 먼저 연결합니다. 제어 가능한 대기나 fixture가 필요하면 준비 범위와 실제 앱 또는 대역의 경계를 표시합니다.

## 인계

- 실행 방법:
- 주요 결정과 코드 위치:
- 확인한 실패 사례:
- 실패 또는 미확인인 필수 조건:
- 다음 행동:

웨이브별 이해 확인이 명시 요청됐다면 위 사람 검증 결과와 대상 상태를 연결합니다. 문답 상태와 제품 통과는 별도로 유지하며, 이해 확인 기록은 기존 작업 보고에 짧게 남깁니다.
