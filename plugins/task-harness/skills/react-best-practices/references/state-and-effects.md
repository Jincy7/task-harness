# 상태와 Effect

## 상태 소유권

- 상태는 사용하는 최소 공통 소유자에 둡니다. 서버 데이터, 폼 초안과 표시 옵션을 구분하며 현재 작업에 불필요한 전역 저장소를 추가하지 않습니다.
- props나 기존 state에서 계산할 수 있는 값은 렌더링 중 계산합니다. 파생 값을 별도 state와 Effect로 맞추는 중복을 피합니다. 이전 상태에 의존한 갱신은 함수형 updater를 사용하고 객체나 배열을 직접 변경하지 않습니다.
- 목록 key에는 안정적인 항목 ID를 사용합니다. 순서가 바뀌는 목록의 index나 렌더링마다 만든 임의 key가 입력 상태를 다른 행에 붙이거나 초기화하지 않는지 확인합니다.
- 컴포넌트를 다른 컴포넌트 함수 안에 정의해 매 렌더링마다 새 타입을 만들지 않습니다. key 변경으로 상태를 초기화할 때는 사용자 초안이 사라지는 시점이 요구사항과 맞는지 확인합니다.

## Hooks와 Effect

일반 Hooks는 함수 컴포넌트 또는 custom Hook의 최상위에서 호출합니다. 조건부 return 뒤나 반복문에서 호출하지 않습니다. React의 `use`처럼 별도 호출 규칙을 가진 API는 지원 버전과 공식 규칙을 확인합니다.

Effect는 구독, 타이머, 외부 위젯 등 외부 시스템과의 동기화에 사용합니다. 클릭으로 발생하는 저장이나 전송은 이벤트 처리 경계에 둡니다. Effect 의존성을 빼거나 lint를 끄는 방식으로 중복 실행을 숨기지 않습니다. 구독과 타이머는 cleanup에서 해제하고 개발 환경의 재설정에도 같은 결과를 유지합니다.

데이터 조회는 프로젝트의 기존 프레임워크나 캐시 방식을 우선합니다. 직접 Effect에서 조회하면 취소와 오래된 응답 무시를 처리합니다. 검색어 A 다음 B를 요청했을 때 늦게 도착한 A가 B의 화면을 덮어쓰지 않아야 합니다. 요청 취소는 이미 수행된 서버 변경의 취소를 보장하지 않습니다.

## 렌더링 비용

렌더 중 I/O나 외부 상태 변경을 하지 않습니다. 실제 느린 조작을 측정한 뒤 연산, 구독 범위와 목록 크기를 확인합니다. `memo`, `useMemo`, `useCallback`을 모든 컴포넌트에 추가하지 않습니다. Compiler 적용 여부와 참조 안정성이 필요한 경계를 확인하고 최적화 전후 동작과 비용을 비교합니다.
