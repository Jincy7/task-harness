# 단일 책임과 모듈 분리

처음 구현할 때 현재 요구의 변경 이유와 상태 소유권을 기준으로 경계를 잡습니다.
파일 수나 함수 길이보다 한 규칙을 바꿀 때 함께 수정해야 하는 범위를 줄이는 데 목적이 있습니다.

## 단일 책임의 기준

단일 책임은 함수마다 한 줄의 동작만 수행한다는 뜻이 아닙니다.
함께 바뀌는 규칙과 불변 조건은 모으고, 서로 다른 이유로 바뀌는 정책과 기술 처리는 분리합니다.
예를 들어 할인 규칙의 변경이 HTTP 응답 작성이나 DB 연결 관리의 수정까지 요구하지 않게 합니다.
하나의 사용자 흐름은 여러 책임을 연결할 수 있으며, 그 순서와 실패 처리를 조정하는 것도 하나의 책임입니다.

모듈은 명시적인 입력과 출력으로 협력하는 코드 묶음입니다.
작은 구현은 같은 파일의 함수로 경계를 표현할 수 있습니다.
책임과 의존성이 독립적으로 커지거나 여러 호출자가 같은 계약을 사용하면 별도 파일로 옮깁니다.

## 구현 전에 정할 경계

기존 구조와 가까운 구현을 먼저 찾고, 현재 흐름의 입력부터 결과까지 따라갑니다.
아래 항목 중 실제로 존재하는 책임의 위치와 소유자를 정한 뒤 첫 동작을 구현합니다.
이 검토를 별도 승인 단계나 새 설계 문서 작성 의무로 만들지 않습니다.
기존 구조로 충분하면 그대로 진행하고, 중요한 선택만 기존 스펙이나 작업 보고에 짧게 남깁니다.

| 책임 | 경계에서 확인할 내용 |
| --- | --- |
| 진입점 | CLI, HTTP, 이벤트의 입력 해석과 출력 변환, 인증 문맥 확보 |
| 업무 규칙 | 검증된 값으로 판단과 계산, 단위와 불변 조건 |
| 흐름 조정 | 호출 순서, 권한 확인, 상태 전이와 실패 처리 |
| 외부 I/O | 저장소, 네트워크, 파일 접근과 자원 수명 |
| 화면 | 사용자 입력, 표시, 로딩과 실패 상태 |
| 관측 | 실행 문맥 전달, 필요한 이벤트와 오류 기록 |

이 표의 각 행이 파일이나 클래스를 하나씩 요구하지는 않습니다.
경계마다 입력, 출력과 예상 실패를 분명히 하고, 상태와 연결을 누가 만들고 갱신하며 정리하는지 정합니다.
모듈 안의 가변 상태나 거대한 공용 context로 경계를 우회하지 않습니다.

## 분리할 시점과 함께 둘 시점

| 코드에서 보이는 신호 | 구현 중 조치 |
| --- | --- |
| 규칙 변경과 저장 방식 변경이 항상 같은 함수에 섞임 | 판단 함수와 I/O 호출 분리 |
| 작은 계산 검증에도 웹 서버, DB, 로거 대역이 모두 필요 | 실제 계산 입력과 결과를 드러내고 부수 효과를 호출부로 이동 |
| 한 모듈에 무관한 업무와 상태 수명이 섞임 | 기능별로 소유권을 나누고 명시적 계약으로 연결 |
| 순환 import나 내부 필드 직접 수정 발생 | 호출 방향과 상태 소유자 재검토, 필요한 값이나 좁은 연산만 공개 |
| 함수들이 같은 불변 조건과 트랜잭션을 함께 지킴 | 하나의 응집된 작업으로 유지, 분리 시에도 원자성 소유자 유지 |
| 짧고 독립적인 계산 또는 단순한 정적 화면 | 현재 함수나 컴포넌트로 유지 |

업무 판단은 가능한 한 HTTP 객체, ORM 모델, 전역 설정이나 UI 컴포넌트를 직접 참조하지 않게 합니다.
진입점이나 조정 코드가 필요한 값과 I/O 함수를 전달합니다.
단순한 함수 인자나 기존 모듈로 충분하면 별도 인터페이스 계층이나 의존성 주입 프레임워크를 만들지 않습니다.
외부 I/O의 재시도와 타임아웃, 트랜잭션과 자원 정리 책임을 여러 계층에 중복 배치하지 않습니다.

## 작은 구현 예시

주문 생성에서 다음 경계를 기존 프로젝트 구조에 맞춰 배치할 수 있습니다.

```text
HTTP 진입점: 입력 해석, 인증된 사용자 확보, 응답 변환
  → 주문 생성 흐름: 권한과 업무 조건 확인, 저장 호출, 결과 반환
      → 가격 계산: 항목과 확정 규칙을 받아 금액 반환
      → 주문 저장: 주문과 재고 변경을 하나의 트랜잭션으로 반영
```

가격 계산은 DB 연결이나 응답 객체 없이 작은 입력으로 확인할 수 있어야 합니다.
재고 조건이 동시 요청의 영향을 받으면 저장 시점에도 원자적으로 확인합니다.
코드를 파일로 나누면서 주문 저장과 재고 반영을 각각 커밋하면 기존 불변 조건이 깨집니다.
저장 함수 내부나 호출자가 트랜잭션을 소유할 수 있지만, 한 작업의 원자성을 책임지는 위치는 분명해야 합니다.
성공 이벤트는 실제 커밋 이후에 기록하고 관측 모듈이 업무 결과를 결정하지 않게 합니다.

React에서는 사용자 흐름별로 상태를 소유하는 컴포넌트를 정하고, 표시 컴포넌트와 데이터 요청 경계를 필요한 만큼 분리합니다.
여러 화면이 공유하는 요청 수명이나 복잡한 외부 동기화가 있으면 기존 데이터 계층 또는 custom Hook으로 모읍니다.
각 `useState`를 별도 Hook으로 감싸거나 모든 JSX 조각을 파일로 만드는 규칙은 두지 않습니다.
화면 편의를 위해 권한이나 저장 규칙을 클라이언트로 옮기지 않습니다.

## 과도한 분리를 피하는 기준

현재 요구에 없는 교체 가능성만을 위해 범용 저장소, 플러그인 구조, 이벤트 버스나 공용 기반 클래스를 도입하지 않습니다.
단순 전달만 하는 계층은 명확한 계약이나 경계 역할이 있는지 확인하고, 없으면 합칩니다.
코드 모양이 비슷해도 변경 이유가 다르면 성급하게 공통화하지 않습니다.
공용 `utils`에 서로 무관한 업무 규칙을 모으지 않으며, 기능 이름과 실제 책임으로 위치를 설명합니다.
파일 개수나 줄 수를 품질 기준으로 삼지 않습니다.

구현 중 책임이 섞인 것을 발견하면 현재 변경 범위 안에서 작은 추출로 정리합니다.
광범위한 기존 구조 변경은 현재 수용 조건에 필요한지 먼저 판단하고, 무관한 리팩토링을 함께 진행하지 않습니다.
새 기능의 필수 경계를 모두 나중의 리팩토링으로 미루지 않습니다.

## 흐름 완료 때 확인할 내용

- 현재 요구의 규칙 변경이 화면, 저장 기술과 불필요하게 얽히지 않는지 확인합니다.
- 업무 규칙은 작은 입력으로, 저장과 외부 호출은 해당 경계에서, 사용자 흐름은 연결된 경로에서 검증합니다.
- 상태, 트랜잭션, 재시도와 자원 정리의 소유자가 분명한지 확인합니다.
- 모듈 분리 후에도 입력, 출력, 오류, 권한과 원자성 계약이 유지되는지 확인합니다.
- 파일을 옮겼거나 mock을 통과했다는 이유만으로 동작 검증을 완료 처리하지 않습니다.

구조 점검은 매 파일마다 별도 보고서를 만드는 절차가 아닙니다.
웨이브나 작은 사용자 흐름을 마칠 때 확인하며, 중요한 변경과 남은 구조 문제만 기존 작업 보고에 기록합니다.
