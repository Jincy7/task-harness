# 검증 가능한 작업 단위로 커밋

Git 저장소에서는 하나의 동작이나 수정 목적을 검증하고 독립적으로 검토 및 되돌릴 수 있는 크기로 작업과 커밋을 나눕니다.
사용자가 커밋 보류, 금지 또는 별도 규칙을 지정하면 그 지시를 따릅니다.
Git이 없는 프로젝트에 이 지침만을 이유로 저장소를 만들지는 않습니다.

## 커밋 경계 정하기

작업을 시작할 때 현재 체크리스트에서 함께 완료되어야 하는 변경을 찾습니다.
작은 흐름 하나는 한 커밋일 수 있고, 여러 목적이 섞인 웨이브는 여러 커밋으로 나눌 수 있습니다.
파일 수나 수정 줄 수, 일정한 시간 간격으로 커밋을 나누지 않습니다.

| 변경 | 커밋 단위 |
| --- | --- |
| 새 업무 규칙 | 규칙 구현, 관련 테스트와 필요한 계약 문서 |
| 저장 실패 수정 | 원인 수정과 실패 후 상태를 확인하는 회귀 테스트 |
| 화면 동작 추가 | 사용 가능한 화면 흐름과 해당 상태 및 조작 검증 |
| 동작을 바꾸지 않는 모듈 추출 | 이동, import 및 호출부 변경, 기존 동작 유지 확인 |
| 독립적인 규칙 추가 두 개 | 각각 검증 가능한 두 커밋 |

구현만 먼저 커밋하고 필수 테스트나 호출부 수정을 뒤 커밋으로 미루지 않습니다.
반대로 기능 구현, 무관한 버그 수정, 대규모 포맷 변경을 한 커밋에 섞지 않습니다.
준비 리팩토링이 독립적으로 동작을 유지하면 먼저 커밋하고 기능 변경을 이어갑니다.
작은 추출이 기능과 함께 있어야 의미가 있으면 같은 커밋에 둡니다.

DB 스키마, 공개 인터페이스와 호출부가 함께 바뀌어야 한다면 같은 커밋으로 묶거나 기존 호출도 지원하는 중간 단계를 만듭니다.
중간 커밋에서 빌드나 동작 계약이 깨지는 분할을 피합니다.
순서에 의존하는 커밋은 그 관계를 설명합니다. 독립적인 검토 단위라는 이유로 서로 무관한 순서로 적용할 수 있다고 주장하지 않습니다.

## 구현 중 반복하는 절차

1. 현재 목적에 필요한 변경만 구현합니다.
2. 관련 테스트와 검사로 결과를 확인합니다. 문서 변경은 링크, 예시와 계약을 확인합니다.
3. 현재 변경과 staged diff를 읽어 사용자 변경이나 다른 작업의 파일이 섞이지 않았는지 확인합니다. 필요한 파일이나 변경 구간만 stage합니다.
4. 무엇을 바꿨는지 드러나는 메시지로 커밋합니다. 목적과 검증 근거가 필요한 경우 본문에 간단히 남깁니다.
5. 브랜치, 커밋 SHA와 검증 결과를 보고한 뒤 다음 작업으로 넘어갑니다. 전체 구현이 끝난 뒤 큰 변경을 한 번에 커밋하는 방식으로 미루지 않습니다.

검사 실패를 성공으로 기록하거나 커밋 hook을 임의로 우회하지 않습니다.
환경 문제로 검증이 막혔다면 실행하지 못한 항목과 이유를 기록합니다.
이때 작업 보존용 커밋을 만들 수 있지만 검증 완료나 수용 조건 통과로 처리하지 않습니다.
제품 결함으로 관련 검사가 실패하면 해당 단위를 고친 뒤 완료 커밋을 만듭니다.

커밋이 실패하면 Git 오류와 미커밋 변경을 보고합니다. 작성자 정보 누락과 권한 또는 hook 실패를 구분합니다.
인증 파일 복사, 전역 Git 설정 변경이나 hook 우회를 해결책으로 사용하지 않습니다.
작업을 위임해 worktree에서 커밋을 받았다면 실제 완료 대상 브랜치에 통합됐는지 확인합니다.
SHA를 반환받은 것만으로 통합 완료를 선언하지 않으며, 완료 대상 브랜치의 HEAD와 남은 변경을 확인합니다.

기존 사용자 변경은 덮어쓰거나 임의로 포함하지 않습니다.
같은 파일에 변경이 섞였으면 diff와 문맥을 확인해 자신의 변경만 분리하며, 구분할 수 없으면 그 부분의 커밋을 보류하고 이유를 알립니다.
분리를 위해 사용자 변경을 임의로 stash, reset 또는 discard하지 않습니다.
다른 사람의 커밋이나 이미 공유된 이력을 임의로 amend, squash 또는 강제 push하지 않습니다.

## 기록과 반환

커밋은 코드 이력이고 플랜은 작업 체크리스트입니다.
매 커밋의 diff나 실행 출력을 플랜에 누적하지 않습니다.
중요한 커밋, 검증 근거와 미확인 항목은 기존 작업 보고에서 연결하고, 최종 반환에는 변경 목적과 관련 커밋을 간결하게 안내합니다.

로컬 커밋과 원격 push, PR 생성 및 배포의 권한은 구분합니다.
push 등은 기존 사용자 승인 범위를 따르며, 작은 커밋마다 자동으로 원격 작업을 실행하지 않습니다.
