# Task Build

확정된 작업 하나를 실제로 실행되는 흐름까지 구현합니다. 사용자 행동, 성공 결과, 입력과 상태 변화, 실패 처리를 수용 조건으로 사용합니다.

## 시작과 기록 위치

프로젝트 지침, 현재 변경 사항, 기존 기록과 관련 코드를 확인합니다. 수용 조건이 구현에 충분하면 바로 진행합니다. 빠진 조건이 동작이나 큰 재작업을 좌우할 때만 질문하고 독립적인 작업은 계속합니다.

요구와 가정은 스펙, 할 일은 플랜, 결과는 작업 보고에 둡니다. 기존 경로를 우선하며 새 구조가 필요하면 다음을 사용합니다.

- `docs/specs/<topic>.md`: 입력, 출력, 상태 변화, 실패 경계와 수용 조건 ID
- `docs/plans/<topic>.md`: 작업 ID가 있는 체크리스트, 스펙과 작업 보고 링크
- `docs/reports/<topic>/<work-id>.md`: 변경 결과, 실행 근거, 이상 상황, 원인과 조치, 미확인 사항

플랜에는 작업 계약, 실행 출력, 검증 결과 표나 회고를 누적하지 않습니다. 체크 상태와 보고서 링크만 바꾸고 새 범위가 생길 때 해당 체크 항목을 추가합니다. 범위 변경 이유는 스펙이나 작업 보고에 남깁니다. 기존 `WORK.md`의 이력은 보존하고 새 보고서에서 연결합니다. AGENTS.md는 문서 규칙, 스킬 선택과 일반 쓰기 작업의 완료 조건을 담는 지도로 유지합니다.

## 구현 전에 책임과 모듈 경계 결정

새 흐름을 만들거나 기존 흐름의 책임을 확장하면 [단일 책임과 모듈 분리](references/module-boundaries.md)를 읽습니다.
함께 바뀌는 규칙은 모으고, 다른 이유로 바뀌는 업무 판단, 외부 I/O와 표시 처리는 명시적인 입력과 출력으로 분리합니다.
기존 구조를 우선하며 상태, 트랜잭션과 자원 수명의 소유자를 정합니다.
작은 구현은 같은 파일의 함수로 시작할 수 있습니다. 현재 요구에 없는 계층이나 파일 분할을 강제하지 않습니다.

계산 방식이나 데이터 변경 정책을 다루면 [분석과 변경 계약](references/decision-evidence.md)을 읽습니다.
중요한 분석 요청과 제안의 채택, 수정, 기각은 기존 작업 보고에 결정 주체와 검증 근거를 연결합니다.
이 기록은 이해 확인 요청이 없어도 남기며, 사소한 선택마다 문서를 늘리지 않습니다.

## 구현 도구 선택

UI와 일반 기능에서도 기존 구성요소, 외부 패키지와 직접 구현의 부담을 비교합니다.
현재 요구를 충족하면서 직접 작성하고 검증할 코드가 줄어드는 쪽을 선택합니다.
사용자가 정한 기술 제약, 설치 가능성, 유지보수 및 통합 비용을 확인하고 무의존성이나 특정 패키지를 기본 목표로 삼지 않습니다.
기존 방식으로 충분한 작은 수정에 새 패키지를 추가하지 않습니다.

## 구현 전에 행동 시나리오와 관측 준비

앱이나 CLI를 처음 구현하거나 실행 경계를 바꾸면 [로컬 실행 기록 지침](references/runtime-logging.md)을 읽고 필요한 관측 범위와 도구를 정합니다.
기존 로거를 우선 재사용합니다.
로거가 없으면 필요한 관측 범위를 먼저 정하고, 표준 기능과 외부 패키지 중 직접 관리할 코드와 검증 부담이 줄어드는 쪽을 선택합니다.
무의존성을 강제하지 않으며 선택 이유와 남는 부담은 작업 보고에 짧게 기록합니다.

먼저 사전 상태, 사용자 행동 순서와 기대 결과를 정하고 요청 및 상태 변화의 관측 지점을 연결합니다.
시작 이벤트와 안전한 실패 하나가 해당 실행의 파일에 남는지 확인한 뒤 업무 흐름을 구현합니다.
이 연결 확인은 행동 검증을 대신하지 않습니다.
이미 검증된 기록 경로는 다시 만들지 않습니다.
문서나 단순 정적 수정에 앱 로거를 추가하지 않습니다.
기록 준비가 막히면 이유와 남길 수 있는 실행 출력을 작업 보고에 적고, 관측 도구를 만드는 일로 독립적인 구현을 중단하지 않습니다.

## 구현과 검증

Git 저장소에서는 [커밋 단위 지침](references/commit-units.md)에 따라 하나의 동작이나 수정 목적을 검증 가능한 크기로 나눕니다.
각 단위의 구현, 필요한 테스트와 문서를 함께 확인하고 커밋한 뒤 다음 작업으로 넘어갑니다.
사용자의 커밋 보류 지시와 기존 변경을 보존하며, 파일별 분할이나 전체 작업 종료 후 일괄 커밋을 기본으로 삼지 않습니다.

1. 정한 책임 경계를 지키면서 입력부터 업무 규칙, 저장 또는 결과 표시까지 연결합니다. 골격이나 고정 응답만으로 흐름을 완료 처리하지 않습니다.
2. 현재 수용 조건에 맞는 행동 시나리오를 실행합니다. 입력 수정, 중복 요청, 실패 후 재시도, 새로고침이나 늦은 응답 중 해당하는 경계를 확인합니다. 저장 성공 이벤트는 실제 커밋 이후에 남기고, 응답과 독립적인 저장 상태 조회 또는 화면 관측을 기대 결과와 대조합니다.
3. 변경에 맞는 단위 테스트, HTTP/API 통합 테스트, 빌드나 정적 검사를 실행합니다. 각 실행의 종료 상태와 원문 근거 위치를 남깁니다. UI 직접 확인이 필요하면 조작과 기대 결과를 기록합니다.
4. 실행 뒤 종료 코드, 구조화된 오류, 타임아웃, assertion 결과와 로그 수집 상태를 확인합니다. 예상한 실패와 예상 밖 실패를 구분하고, 오류가 없다는 이유만으로 수용 조건을 통과시키지 않습니다.
5. 이상 상황은 재현 입력과 증거를 확보한 뒤 원인 가설을 세우고 최소 수정으로 확인합니다. 작업 보고에 현상, 근거, 가설 또는 확인된 원인, 조치, 재검증과 남은 한계를 남깁니다. 해결되지 않은 같은 실패를 새 근거 없이 반복하지 않습니다.

도구 실패나 실행 제한을 성공으로 바꾸지 않습니다. 실행하지 못한 검사는 이유와 다음 확인 방법을 남깁니다. 같은 코드와 입력에 대한 수정 전후 실행을 구분하고, 검증 후 코드가 바뀌면 영향받는 검사를 다시 수행합니다. 사용자의 다른 변경을 되돌리지 않습니다.

직접 사용할 앱은 실제 프로젝트 명령으로 개발 환경을 준비하고 실행 위치, 포트와 경로를 README에 안내합니다.
서버 시작과 기능 검증 성공은 구분합니다.
외부 배포나 터널을 기본 의존성으로 추가하지 않습니다.
UI 검증에는 허용되고 사용 가능한 브라우저 자동화 도구를 선택할 수 있으며 특정 도구의 설치를 필수로 만들지 않습니다.
인터페이스 계약은 스펙에, 실제 실행 결과는 작업 보고에 둡니다.

업무 가정이 정정되면 현재 수용 조건을 갱신하고 정정 근거, 영향받는 구현과 최소 회귀 사례를 작업 보고에 연결합니다. 예전 보고의 통과는 보존하며 새 기대값은 확정 규칙에서 도출합니다.

사람이 조작하기 어려운 검증은 기존 도구, 작은 fixture나 제어 가능한 대기 상태로 준비합니다. 실제 앱 경로를 재사용하고 별도 업무 계산을 만들지 않습니다. 진입 위치, 입력, 조작, 기대 결과, 초기화와 대역의 범위를 안내합니다. 응답 전달 보류는 서버 중복 처리나 취소의 검증과 구분합니다.

이해 확인이 명시 요청되면 구현 중에는 사람의 결정만 기록하고 기본 문답은 통합 흐름 완성 뒤에 연결합니다.
웨이브별 확인까지 명시 요청된 작업에서는 사람 검증 뒤 해당 동작과 내부 흐름을 확인하도록 대상과 근거를 인계합니다.
사용자가 확인 중인 코드, 서버와 입력을 유지하면서 독립 작업은 계속합니다. 같은 포트나 hot reload 대상 파일을 조용히 바꾸지 않고, 필요하면 별도 사본과 포트를 사용합니다. 분리가 어려우면 영향을 주지 않는 작업부터 진행하며 실제 병행 여부를 정확히 알립니다.

## 선택적 위임

메인 에이전트 한 명으로 시작합니다. 인터페이스가 고정되고 수정 파일이 겹치지 않거나 독립 검토가 필요한 경우에만 사용 가능한 도구와 위임 권한을 확인합니다. 위임하거나 같은 저장소에서 여러 세션이 쓰기 작업을 할 때 [작업 계약](references/delegation-template.md)을 읽습니다.

작업자는 기존 변경을 보존해야 합니다. 메인은 같은 파일을 동시에 수정하지 않고 결과를 통합합니다. 위임 도구가 없으면 순차 수행하며, 작업마다 별도 구현자나 문서 작성자를 만드는 절차는 두지 않습니다.

## 완료와 반환

웨이브나 작은 사용자 흐름을 마칠 때 책임이 섞이거나 순환 의존성이 생겼는지 확인합니다. 현재 범위의 필요한 추출은 구현 중에 정리하고, 분리 후에도 권한, 오류와 원자성 계약이 유지되는지 검증합니다. 구조 점검 결과는 중요한 선택과 남은 문제만 작업 보고에 남깁니다.

현재 수용 조건의 실행 근거가 있으면 체크 항목을 완료로 바꾸고 작업 보고를 연결합니다. 구현 위치, 실행 결과, 이상 상황의 처리, 실패 또는 미확인과 남은 한계를 반환합니다. 구현 완료와 검증 완료를 구분합니다.

하네스는 별도 모델, MCP, hooks, 자동 업데이트, 외부 로그 전송을 요구하지 않습니다. Push, PR 생성, 배포와 메시지 전송은 사용자의 별도 요청과 실행 환경의 권한을 따릅니다.
