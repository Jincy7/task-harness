# Task Build

확정된 작업 하나를 실제로 실행되는 흐름까지 구현합니다. 사용자 행동, 성공 결과, 입력과 상태 변화, 실패 처리를 작업 계약으로 사용합니다.

## 시작과 작업 계약

프로젝트 지침, 현재 변경 사항, 기존 기록과 관련 코드를 확인합니다. 수용 조건이 구현에 충분하면 바로 진행합니다. 빠진 조건이 동작이나 큰 재작업을 좌우할 때만 그 조건을 질문합니다. 독립적인 구현은 계속합니다.

구현 전에 다음 내용을 짧게 기록합니다.

- 목표와 수용 조건 ID
- 입력, 출력, 상태 변화와 기존 인터페이스
- 수정할 파일과 범위 밖 작업
- 통과하는 주요 경계와 실패 처리
- 완료 조건과 실제 실행할 검증 명령

프로젝트 지정 기록을 사용하고, 없으면 `docs/plans/<topic>.md`에 계약과 결과를 기록합니다. 요구는 기존 스펙의 ID와 링크로 참조합니다. 기존 `WORK.md`나 별도 작업 장부가 있으면 그것을 유지하고 연결하며 같은 상태표를 복제하지 않습니다.

현재 작업에 필요한 문서만 갱신합니다. 중요한 결정 이유는 기존 ADR 경로나 `docs/adr`에 기록하되 일상적인 선택마다 만들지 않습니다.

## 구현과 검증

1. 입력부터 업무 규칙, 저장 또는 결과 표시까지 연결합니다. 골격이나 고정 응답만으로 흐름을 완료 처리하지 않습니다.
2. 현재 흐름이 통과하는 경계에서 실패 사례를 고릅니다. 입력 검증, 저장 실패와 재시도, 중복 요청, 모듈 간 필드와 오류 의미를 실제 경계에 맞춰 확인합니다.
3. 변경에 맞는 단위 테스트, HTTP/API 통합 테스트, 빌드나 정적 검사를 실행합니다. UI의 직접 확인이 필요하면 조작과 기대 결과를 남깁니다. 브라우저 자동 조작을 기본 검증 의존성으로 추가하지 않습니다.
4. 실패는 재현 입력과 관측을 확보한 뒤 원인 가설을 세우고 최소 수정으로 확인합니다. 해결되지 않은 같은 실패를 새 근거 없이 반복하지 않습니다.
5. 새 요구는 현재 계약의 결함인지 다음 작업인지 구분합니다. 현재 수용 조건을 바꾸면 이유와 영향을 기록하고 관련 검증을 다시 실행합니다.

도구 실패나 실행 제한을 성공으로 바꾸지 않습니다. 실행하지 못한 검사에는 이유와 다음 확인 방법을 기록합니다. 사용자의 다른 변경을 되돌리지 않습니다.

직접 사용 확인이 필요한 앱은 실제 프로젝트 명령으로 개발 환경을 준비하고 실행 위치, 포트와 경로를 기록합니다. 서버 시작과 기능 검증 성공을 구분합니다. 바인딩은 해당 환경의 접근 방식에 맞추고 외부 배포나 터널을 자동 추가하지 않습니다. 컴포넌트 경계는 현재 흐름의 입력, 출력, 오류 의미로 플랜에 기록합니다.

## 선택적 위임

메인 에이전트 한 명으로 시작합니다. 인터페이스가 고정되고 수정 파일이 겹치지 않거나 독립 검토가 필요한 경우에만 보조 에이전트 한 명을 고려합니다. 사용 가능한 도구와 위임 권한을 먼저 확인합니다.

위임할 때만 [작업 계약](references/delegation-template.md)을 읽습니다. 작업자는 다른 작업자가 있음을 알고 기존 변경을 보존해야 합니다. 메인은 같은 파일을 동시에 수정하지 않고, 결과를 통합하며 기록의 최종 반영을 담당합니다. 위임 도구가 없으면 같은 계약으로 순차 수행합니다. 문서별 상시 작성자나 작업마다 별도 구현자와 리뷰어를 만드는 절차는 두지 않습니다.

## 완료와 반환

현재 수용 조건의 실행 근거가 있으면 완료입니다. 구현 위치, 실행한 명령과 관측, 실패 또는 미확인, 남은 한계를 반환하고 기록을 갱신합니다. 검증이 막혔으면 구현 상태와 검증 상태를 구분합니다.

하네스는 별도 모델, MCP, hooks, 자동 업데이트, 외부 로그 전송을 요구하지 않습니다. Push, PR 생성, 배포, 메시지 전송을 이 스킬의 기본 단계로 추가하지 않습니다. 외부 작업은 사용자의 별도 요청과 실행 환경의 권한을 따릅니다.
