# 대화 분기와 예제

한 응답에는 현재 질문의 피드백과 다음 질문 하나만 둡니다. 질문을 제시한 뒤 실제 사용자 응답을 기다립니다.

| 응답 | 다음 행동 |
| --- | --- |
| 의미와 이유가 정확 | 맞는 판단을 짧게 확인하고 다음 핵심 경계로 이동 |
| 결과만 정확 | 이유나 중간 상태 하나를 보충 질문 |
| 일부 혼동 | 맞는 부분 유지, 혼동된 판단 구분, 작은 예제 후 다른 사례 |
| 모르겠음 또는 설명 요청 | 짧은 설명, 구체적 예제, 새 조건에 적용하는 질문 |
| 애매한 표현 | 의미 확인 질문 하나, 오답 단정 금지 |
| 실제 동작의 모순 지적 | 규칙과 코드 및 관측 대조, 제품 문제와 설명 부족 구분 |
| 생략 또는 종료 | 상태와 재개 위치 보존, 사용자 요청에 따라 이동 |

예제는 확정 규칙에서 도출합니다. 실행하지 않은 예제는 개념 설명용이라고 밝힙니다. 코드가 현재 그렇게 동작한다는 사실만으로 규칙의 타당성을 확정하지 않습니다.
여러 번 혼동하면 같은 설명을 늘리지 말고 입력과 결과를 작은 표나 흐름으로 나눕니다. 더 진행하지 않겠다는 요청은 존중합니다.

## 합성 대화 예시

상황: 사용자가 대기 중 중복 클릭 방지를 직접 확인했습니다. 현재 구현에는 요청 추적 ID와 버튼 잠금이 있고 서버의 재전송 중복 처리는 없습니다.
아래 응답은 예시이며 실제 사용자 답이나 검증 결과가 아닙니다. 실제 사용에서는 각 질문에서 멈춥니다.

에이전트: 방금 대기 중 다시 눌러도 요청이 하나만 나가는 것을 확인했습니다. 버튼을 잠그는 처리가 어느 경계에서 중복을 막는지 설명할 수 있을까요?

사용자: 요청 ID도 있으니 서버에서도 한 번만 처리하는 것 같습니다.

에이전트: 화면에서 다시 누르는 동작은 막지만, 요청 ID는 현재 요청을 추적하는 데 사용합니다. 같은 ID의 처리 결과를 보관하고 재사용하는 서버 기능은 아직 없습니다. 개념 예제로, 서버 처리는 끝났는데 응답만 끊긴 경우를 생각해 보겠습니다. 현재 구현에서 같은 작업을 다시 전송하면 서버가 두 번 처리할 가능성이 있을까요?

사용자: 다시 처리할 수 있겠네요.

에이전트: 맞습니다. 버튼 잠금과 서버의 재전송 처리를 구분한 설명입니다. 이번에는 다른 브라우저에서 동일한 입력을 보낸다면, 첫 브라우저의 버튼 잠금이 그 요청도 막을 수 있을까요?

후속 질문은 이해를 새 사례에 적용하는 목적입니다. 정답을 직접 말한 직후 사용자의 동의를 전체 이해 완료로 기록하지 않습니다.

## 최종 모드에서의 확인

최신 버전의 실제 보장을 확인한 뒤 질문합니다. 예를 들어 서버 멱등성이 후속 웨이브에서 구현됐다면 이전의 미구현 설명을 그대로 사용하지 않습니다.
전체 흐름의 질문 다음에는 이전에 혼동한 경계나 실패 후 복구를 새로운 사례로 묻습니다. 질문 순서와 개수를 고정하지 않습니다.
사람 검증이 남은 최신 화면은 그 상태로 기록하며, 과거 화면을 보았다는 사실로 최신 화면 확인을 대체하지 않습니다.

## 짧은 기록 예시

기존 보고에 필요한 행만 남깁니다. 다음 표는 빈 형식이며 사용자 응답 없이 결과를 채우지 않습니다.

| 대상 / 규칙 | 사례와 답변 요지 | 보완과 변형 사례 | 상태 / 다음 질문 |
| --- | --- | --- | --- |
| | | | |

확인 대상의 코드 상태, 실행 주소, 사람 검증 근거는 기존 보고의 정보를 참조합니다. 힌트로 도운 부분과 독립 적용을 구분합니다.
완료한 설명 확인과 제품의 자동 및 사람 검증 결과를 한 상태로 합치지 않습니다.
