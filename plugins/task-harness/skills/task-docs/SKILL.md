# Task Docs

현재 작업의 요구, 구현 순서, 결정 이유, 구조를 찾을 수 있도록 문서를 정리합니다. 필요한 문서만 작성하고, 전체 문서 완성이나 승인을 구현 시작 조건으로 추가하지 않습니다.

## 먼저 확인할 것

사용자 요청, 적용 지침, 기존 문서와 코드, 현재 변경 사항을 읽습니다. 문서에 적힌 이전 완료 보고는 현재 실행 근거와 구분합니다. `docs/spec`, `docs/plan`, `docs/decisions` 등 기존 경로와 제출 형식은 그대로 유지합니다.

문서만 요청받았다면 문서 범위에서 마칩니다. 구현까지 요청받았다면 첫 흐름의 사용자 행동, 성공 결과, 입력과 상태 변화, 실패 처리가 정해지는 즉시 해당 구현을 이어갑니다. 문서 정비가 끝날 때까지 독립적인 구현을 기다리게 하지 않습니다. 읽기 전용 요청에서는 파일을 수정하지 않고 제안을 반환합니다.

## 기록 위치

기존 구조가 없을 때만 아래 경로를 기본으로 사용합니다. 빈 디렉터리나 모든 종류의 문서를 미리 만들지 않습니다.

| 위치 | 정보의 원본 |
| --- | --- |
| `docs/README.md` | 현재 작업과 관련 문서를 찾는 지도 |
| `docs/specs/<topic>.md` | 기대 동작, 범위, 수용 조건 ID, 질문과 가정 |
| `docs/plans/<topic>.md` | 현재 흐름의 구현 순서, 작업 담당과 상태, 경계, 검증 근거 |
| `docs/adr/0001-<decision>.md` | 중요한 결정과 근거, 대안, 구현, 검증과 한계 |
| `docs/diagrams/<topic>.*` | 그림이 설명에 도움이 되는 관계 |

`AGENTS.md`는 문서 작성 규칙과 스킬 사용 시점을 연결하는 지도로 유지합니다. 구현 현황, 명령 목록과 테스트 결과는 이 지도에 복제하지 않습니다.

각 정보의 원본은 한 곳에 둡니다. 기존 작업 장부나 `WORK.md`가 있다면 유지하고 플랜에서 연결합니다. 같은 상태표를 다시 만들거나 자동 이관하지 않습니다. 스펙의 요구는 플랜에서 ID와 링크로 참조하고 길게 복제하지 않습니다. 검증 명령, 입력, 실제 관측, 미확인 조건은 해당 플랜이나 기존 장부에 남깁니다.

## 작성 절차

1. 현재 작업과 직접 관련된 문서, 빠진 정보, 기록 위치를 정합니다. 초기 정리는 약 3분을 목표로 작게 시작하되, 시간 경과로 미확정 사실을 확정하지 않습니다.
2. 새 문서가 필요한 경우에만 [문서 템플릿](references/document-templates.md)에서 해당 부분을 사용합니다. 현재 흐름만 구체화하고 이후 흐름은 짧게 남깁니다.
3. 데이터 구조나 이후 구현을 바꾸는 선택, 이유를 보존할 중요한 결정에만 ADR을 작성합니다. 번호는 기존 문서에서 확인해 중복을 피합니다. 일상적인 파일명이나 변수명 선택마다 만들지 않습니다.
4. 현재 유효한 동작은 스펙에, 선택 이유는 ADR에 둡니다. 결정을 바꾸면 스펙을 갱신하고 이전 ADR의 대체 상태와 새 ADR의 양방향 링크를 남깁니다. 과거 이유를 지우지 않습니다.
5. 관계를 그림으로 설명해야 할 때만 [다이어그램 지침](references/diagrams.md)을 읽습니다. 링크, 요구 ID, 경로, 코드와 문서의 일치 여부를 확인합니다. 테스트 결과는 실제 관측 범위만 기록합니다.

## 협업과 종료

메인은 인터뷰와 결정 확인, 결과 통합을 담당합니다. 위임이 허용되고 도움이 되는 독립 문서에만 보조 작성자를 둘 수 있습니다. 파일마다 편집 책임자를 한 명 정하고 동시에 수정하지 않습니다. 문서마다 설계, 계획, 리뷰 에이전트를 연쇄 생성하지 않습니다. 다른 작업자의 변경을 보존합니다.

현재 작업을 찾을 문서 지도와 필요한 내용이 갖춰지고 중복 원본, 깨진 링크가 없으면 문서 정리를 마칩니다. 변경 문서, 정보별 원본 위치, 확인 결과와 미확인 사항, 다음 작업을 반환합니다. 문서 작성 완료를 구현 완료로 표시하지 않습니다. 다른 하네스 스킬의 설치나 호출은 필수 조건이 아닙니다.
