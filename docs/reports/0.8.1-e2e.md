# 0.8.1 실제 구현 흐름 검증

2026-10-31에 합성 회의실 예약 요구사항을 새 Git 저장소에 주고 실제 Codex CLI 세션 두 개를 순차 실행했습니다.
에이전트 지침 생성, 범위 정리, 구현, 검증과 중간 커밋을 관측했습니다. 첫 실행에서 작업 커밋 5개, 새 세션의 변경 요청에서 2개를 확인했습니다.
진행 체크는 기본 플랜에서 1/5부터 5/5까지, README를 원본으로 지정한 후에는 6/7에서 7/7로 갱신됐습니다.

기존 Codex 설정을 그대로 사용했고 전역 설정과 인증 파일은 바꾸지 않았습니다.
이 실험은 프로젝트 스킬 복사 경로의 관측이며 플러그인 재설치나 캐시 갱신 검증은 아닙니다.
사용자 환경의 다른 스킬과 MCP 설정도 노출됐으므로 task-harness만 격리한 효과 측정으로 해석하지 않습니다.

### 합성 문제

로그인한 구성원이 회의실을 예약하고 본인 예약을 조회하거나 취소하는 웹서비스입니다. 관리자는 전체 예약을 조회하고 취소합니다.
실제 HTTP 서버, SQLite 저장, 브라우저 화면과 실행 안내를 요구했습니다.

- 허용 시간 `09:00~18:00`, 실제 날짜, 시작보다 늦은 종료, 제목 길이 검증
- 같은 방과 날짜의 `[start,end)` 겹침 거절, 인접 시간 허용
- 동시 예약의 단일 저장, 실패 시 기존 데이터 보존, 취소 후 재예약
- 세션 인증, 소유자 강제 지정, 역할별 조회와 취소 권한
- 서버 재시작 후 예약 보존, 잘못된 입력과 충돌 후 화면 복구

원래 제목 계약은 원문 1~100자였고, 후속 요청에서 앞뒤 공백 제거 후 길이 검사로 바꿨습니다.
실제 계정, 배포나 Docker 요구는 넣지 않았습니다.

## 첫 실행: 지침 생성부터 실제 웹 검증까지

실행기에 전달한 요청은 다음과 같습니다. 커밋, 플랜이나 체크리스트를 별도로 지시하지 않았습니다.

```text
이 저장소의 REQUIREMENTS.md에 있는 회의실 예약 웹서비스를 끝까지 구현하고 검증해줘.
프로젝트 .agents/skills 안에 있는 task-harness 0.8.1을 사용해 $task-agents로 에이전트 지침을 셋업하고, $task-scope로 범위를 정한 뒤 $task-build로 구현하고 $task-verify로 실제 결과를 확인해줘.
요구사항이 충분한 부분은 질문 없이 진행하고, 문서만 작성한 상태에서 멈추지 마. 작업은 이 저장소 안에서 수행하고 전역 설정이나 인증 파일은 변경하지 마.
```

종료 코드는 0, 소요 시간은 327.6초입니다. 아래 시간은 실행 시작 후 HEAD 변경을 관측한 시점이며 정확한 커밋 실행 시각과 최대 약 5초 차이가 납니다.

중간 커밋에 코드, 관련 테스트와 보고가 함께 들어갔습니다. CLI 기록에서 diff 확인, 선택 stage, staged diff 확인과 commit 실행을 확인했습니다.
인증 커밋을 따로 풀어 테스트 3개, 예약 커밋을 따로 풀어 테스트 10개를 통과했습니다.
마지막 커밋의 API 및 기록 테스트 13개와 실제 Chrome 테스트 2개도 별도 폴더에서 다시 통과했습니다.

README에는 실행 방법과 플랜 링크가 생겼지만 체크박스는 없었습니다.
체크 상태의 원본을 `docs/plans/booking.md`에 두는 현재 하네스 기본 규칙과 일치합니다. 따라서 README 체크리스트가 기본으로 자동 생성된다고 설명하면 안 됩니다.

## 후속 새 세션: README 지정과 일반 수정 요청

첫 세션을 이어받지 않고 새 `codex exec`를 실행했습니다. 스킬 이름과 커밋 지시는 넣지 않았습니다.

```text
예약 제목 처리 요구를 변경할게. 앞뒤 공백을 제거해서 저장하고, 제거한 제목이 비어 있거나 100자를 넘으면 400으로 거절해줘. 실패한 요청은 기존 예약을 바꾸면 안 돼. 웹 화면에서도 같은 결과를 확인할 수 있어야 해.
진행 상황은 README에서 바로 보고 싶어. README의 진행 체크리스트를 현재 상태의 원본으로 두고, 기존 플랜 문서는 작업 순서와 관련 문서 링크로 연결해줘. 두 곳에 같은 체크 상태를 중복 관리하지 말아줘. 변경 요구와 검증 근거를 문서에 반영하고 실제로 검증해줘.
```

종료 코드는 0, 소요 시간은 105.9초입니다.

| 35.3초 | `4441a63` | README로 상태 원본 이전, AGENTS와 문서 연결 갱신 | 6/7 | 0개 |

README를 원본으로 정한 사용자 지시가 기본 경로보다 우선했습니다. 플랜은 작업 순서와 관련 링크만 남겼고 AGENTS의 문서 지도도 함께 바뀌었습니다.
제목 규칙 변경 전 실패를 먼저 재현한 뒤 수정했습니다. 과거 보고의 통과 기록은 당시 계약으로 보존하고 현재 요구와 수용 조건을 갱신했습니다.
최종 HEAD는 `29e3193bbea7f0b5d32c5a9b5e4201cc37299aba`이며 작업 트리는 깨끗합니다.

## 제품 동작의 독립 확인

| 검증 | 실제 결과 |
| --- | --- |
| 초기 구현의 외부 HTTP 계약 검사 | 68/68 assertions 통과 |
| 제목 변경 후 외부 HTTP 계약 검사 | 74/74 assertions 통과 |
| 초기 최종 커밋 재실행 | API 및 기록 테스트 13개, 실제 Chrome 테스트 2개 통과 |
| 변경 후 최종 커밋 재실행 | API 및 기록 테스트 15개, 실제 Chrome 테스트 3개 통과 |
| 중간 커밋 재실행 | 인증 3개, 예약까지 10개 통과 |

외부 HTTP 검사는 에이전트가 작성한 테스트와 별도로 요구 계약에서 작성했습니다.
권한, 오류 응답, 실패 시 상태 보존, 겹침과 인접 시간, 취소와 재예약, 동시 요청 6개의 단일 저장, 재시작 보존을 확인했습니다.
후속 검사에서는 공백 제거 저장, 공백만 있는 제목의 거절, 제거 후 100자 경계도 대조했습니다.
68개와 74개는 assertions 수이며 서로 중복되는 회귀 검사입니다.

생성된 통합 테스트는 SQLite를 별도 연결로 조회하고, 두 서버 프로세스에 보낸 겹치는 요청 8개 중 한 건만 저장되는지 확인합니다.
DB 실패 주입 후 롤백과 재시도도 검사합니다. 브라우저 테스트는 역할별 세션, 데스크톱과 모바일, 충돌 후 입력 보존, 취소, 새로고침, 네트워크 실패 복구를 실행합니다.
화면에서 중복 클릭을 막는 검증과 서버의 트랜잭션 검증을 구분했습니다.

## 발견한 문제와 판정 범위

실제 브라우저에서 파비콘의 CSP 위반을 발견했습니다. 에이전트가 로컬 SVG로 바꾸고 예상 밖 콘솔 오류를 assertion에 추가한 뒤 재실행했습니다.
첫 UI 검사 통과만으로 종료하지 않고 콘솔 근거에서 문제를 찾아 수정한 사례입니다.

후속 세션은 처음에 기존 제목 길이 검사를 HTML `maxlength`라고 잘못 설명했습니다.
실제 코드에는 JavaScript 검사가 있었고, 에이전트가 다음 진행 보고에서 스스로 정정했습니다. 최종 diff와 W07 보고는 실제 변경과 일치합니다.
중간 설명도 코드 근거와 대조해야 한다는 한계가 관측됐습니다.

작업 스킬의 명시 호출 정책 전달에는 빈틈이 있습니다.
생성된 AGENTS에는 상황별 스킬 표와 일반 커밋 조건이 있지만 작업 스킬의 명시 호출 제한이 명확히 적히지 않았습니다.
후속 일반 수정 요청에서 에이전트가 `task-build`, `task-verify`, `task-docs`, `task-agents`를 자발적으로 읽고 적용했습니다.
따라서 새 세션의 실제 커밋은 확인했지만, 이를 “커밋 조건만 계승하고 작업 스킬은 자동 적용하지 않은 실행”의 근거로 사용할 수 없습니다.
이번 작업은 실험과 보고이며 이 관측을 숨기기 위한 하네스 규칙 변경은 하지 않았습니다.

초기 CLI의 최종 응답에는 개발 서버가 실행 중이라는 안내가 있었으나 외부 평가 종료 시점에 해당 포트의 리스너는 없었습니다.
지속 실행은 검증 결과에 포함하지 않으며 앱을 보려면 생성 저장소 README의 명령으로 다시 시작해야 합니다.

단일 문제와 두 순차 세션의 관측입니다. 모든 모델 실행의 커밋 준수율, 병렬 worktree 통합, 운영 인증과 부하, 다른 브라우저, 최종 문답의 효과를 확인한 결과는 아닙니다.
스킬 패키지 자체가 커밋이나 README 갱신을 강제하는 실행기를 제공하는 것도 아닙니다.

원본 실행 자료는 Git에서 제외한 [실험 디렉터리](../../.local/runs/0.8.1-e2e/)에 보존합니다.

임시 제품 저장소가 없어지면 로컬 bundle에서 복원할 수 있습니다. 원본 로그와 가상 환경은 bundle에 포함되지 않습니다.
원본 실행 자료는 로컬에만 있으므로 이 보고서의 Git 복사본만으로 접근할 수 있다고 가정하지 않습니다.

```sh
git clone .local/runs/0.8.1-e2e/project.bundle /tmp/task-harness-booking-replay
cd /tmp/task-harness-booking-replay
python3 -m unittest discover -v
```

실제 브라우저 재검증은 복원한 README의 Playwright 설치 및 실행 명령을 따릅니다.
이번 확인을 위해 기존 훈련 저장소의 제품 코드나 실행환경 설정은 변경하지 않았습니다.
